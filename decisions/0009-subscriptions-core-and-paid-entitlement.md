# ADR 0009: Subscriptions core and paid entitlement semantics (BE-005)

## Status

Accepted

## Context

В ADR 0007 и 0008 была зафиксирована модель доступа к темам `demo | free | paid`.
Уровень `paid` требует авторизованного пользователя с активной подпиской/entitlement
(`apps.subscriptions.policy.has_paid_content_entitlement(user)`), однако точные
статусы, правила истечения, пересечения подписок, поведение триала и границы
API оставались `TBD`.

Данное решение фиксирует авторитарные решения владельца проекта (D1–D8) для ядра
подписок MVP (BE-005) до интеграции платёжного провайдера (BE-006).

## Decision

### D1. Статусы подписки и вычисление истечения
- В БД сохраняются только два статуса: `ACTIVE` и `CANCELLED`.
- Отдельный персистентный статус `EXPIRED` не хранится. Истечение подписки всегда
  вычисляется динамически по времени:
  `starts_at <= now < expires_at`.
- Entitlement предоставляется тогда и только тогда, когда:
  `status in (ACTIVE, CANCELLED)` и `starts_at <= now < expires_at`.
- После `now >= expires_at` доступ отсутствует независимо от сохранённого статуса.
- Фоновые воркеры (cron, Celery) для перевода записей в `expired` в MVP запрещены.
- Статус `CANCELLED` реализует семантику cancel-at-period-end: отменённая подписка
  продолжает давать доступ до наступления `expires_at`.

### D2. Маппинг Plan → Paid Entitlement
- Любой активный/валидный план (`Plan`) предоставляет полный доступ ко всему контенту
  уровня `paid`.
- Не вводятся capability codes, таблицы прав доступа, per-topic ACL или отдельные
  флаги `paid` на дочерних сущностях (блоках, карточках, тестах).
- Все проверки доступа в `content`, `learning` и `media` продолжают полагаться
  исключительно на фасад `apps.subscriptions.policy.has_paid_content_entitlement(user)`.

### D3. Множественные и пересекающиеся подписки
- У одного пользователя может быть несколько записей `Subscription`, включая
  пересекающиеся по времени.
- Ограничение «ровно одна активная подписка на пользователя», exclusion constraints
  PostgreSQL, расширение `btree_gist` и блокировки в BE-005 не вводятся.
- Entitlement активен, если найдена хотя бы одна запись, удовлетворяющая условию D1.
- Если одновременно валидно несколько записей, функция `get_active_subscription()`
  для возврата в `/current/` детерминированно выбирает запись с наиболее поздним
  `expires_at`, а при равенстве — с наибольшим (самым новым) `id` (`order_by("-expires_at", "-id")`).
- Продление концептуально создаёт новую запись `Subscription`.

### D4. Триал
- Триал в MVP не реализуется: поля `Plan.is_trial`, `Subscription.is_trial`,
  `trial_used_at`, эндпоинты активации триала и автоматическая проверка eligibility
  отсутствуют.
- Архитектурное требование: добавление триала в будущем (вместе с BE-006) должно быть
  возможным без изменения базового контракта доступа `demo/free/paid`.

### D5. Отмена подписки (Cancellation)
- Используется модель cancel-at-period-end.
- Статус `CANCELLED` не означает немедленный отзыв доступа: пока `now < expires_at`,
  пользователь сохраняет entitlement.
- При наступлении `now >= expires_at` доступ прекращается.
- Пользовательский эндпоинт отмены подписки в BE-005 не создаётся (откладывается до
  интеграции платёжного шлюза).

### D6. Удаление аккаунта и retention
- Связь `Subscription.user` использует `on_delete=models.CASCADE`.
- При удалении пользователя все его записи `Subscription` удаляются каскадно.
- Финансовые сущности (транзакции, чеки, провайдерский аудит) относятся к BE-006
  и будут подчиняться отдельной политике хранения и деперсонализации.

### D7. Пользовательское API
- В BE-005 реализуются строго два эндпоинта:
  - `GET /api/v1/subscriptions/plans/` — публичный список доступных тарифов (`AllowAny`);
  - `GET /api/v1/subscriptions/current/` — статус доступа и активная подписка текущего
    пользователя (`IsAuthenticated`).
- Эндпоинты покупки, отмены, истории платежей или триала в BE-005 не входят.

### D8. Django Admin
- Предоставляется полноценное ручное управление `Plan` и `Subscription` в панели
  администратора Django для персонала/кураторов:
  - создание и включение/выключение планов;
  - назначение подписок пользователям;
  - редактирование `starts_at`, `expires_at` и переключение статуса (`ACTIVE` / `CANCELLED`).
- Django Admin является операционным инструментом и не отменяет правила entitlement policy.
